# 图生 3D 角色流水线

## 这个技能解决什么

手写几何体（旋转体、LatheGeometry、拼球体）在数学上做了两件做不到的事：
**前后左右完全对称**，以及**四肢只能插在身体上**。所以做出来的东西总是"不像"。

图生 3D 能给出前后不对称的肚子、前伸的下颌、膝盖的拐点、从躯干长出来的四肢。
代价是：换个工具后要处理一堆新问题——几十 MB 的体积、无骨骼、贴图里的五官位置
和你以为的不一样、碰撞盒对不上。这个技能就是这些问题的完整解法。

**判断是否该用**：用户手里有参考图（照片、立绘、截图），且抱怨"不像"、"太丑"、
"像玩具"。若用户只是想调颜色/换尺寸，不要动用这条流水线。

## 流水线总览

```
参考图  →  图生3D  →  GLB(20MB+)  →  压缩内嵌  →  运行时解析  →  接进游戏
 Step 1    Step 2      Step 3        Step 4        Step 5       Step 6
```

全程约 20~40 分钟，其中生成占 5~15 分钟/个，是唯一不可压缩的部分。
**Step 1 的质量决定 70% 的最终效果**，别急着提交。

## Step 1：准备参考图（决定成败）

放进 `res/ref3d/` 这类目录之前，逐条核对：

- **正面全身**，站姿或自然姿势，四肢不交叠遮挡躯干
- **纯色底**，白底最佳；背景越干净，生成的轮廓越准
- 长边 ≥ 1024px；原图糊就先用图像工具放大
- 一图一角色，多角色合影会被糊成一坨
- 只有半身/头像时，**必须先用图生图补全身**（见 `references/reference-image.md`
  里的补图 prompt 模板）。补图不是重画：把发色、瞳色、服装、配饰逐条写死，
  否则会生成一个"同风格但不同人"的新角色

两个常见事故：

- 生成图**右下角带平台水印**。不要裁剪（会切掉鞋底/脚掌），改用采样背景色涂平
- 原图**趴姿/坐姿/侧身**时，横向尺寸会远大于高度。这会直接毁掉 Step 6 的缩放（见下）

## Step 2：提交图生 3D

通过 `buddy-multimodal-generation` 技能走 image-to-3D。参数组合：

| 参数 | 取值 | 说明 |
|---|---|---|
| model | `3.0` | **`3.1` 不支持 LowPoly** |
| generateType | `LowPoly` | 面数 1 万上下，游戏里够用 |
| enablePbr | `true` | 有 PBR 贴图才有立体感，别关 |

一键脚本：`scripts/gen_actor_3d.py`（批量扫目录、断点续传、超限停止）。

**必须知道的硬约束**：

1. **每天 5 次提交额度**，维度 `hy-3d`。这是**次数**限制，不是余额——
   账户里积分再多，第 6 次也提不上去。超限返回 `HTTP 429` +
   `daily submit limit exceeded (5/5)`。按**自然日 0 点**重置，不是提交后 24 小时。
2. 所以**提交顺序很重要**：先跑"图最差、必须补图"的那几个，把一次成型的高质量图放后面。
   顺序反了会出现"最容易的占了额度，最难的没排上"。
3. 生成要 5~15 分钟，**超过多数脚本的轮询上限**。提交成功的第一件事是把 `JobId` 写盘，
   之后只查不重提。中途被杀也不浪费额度。
4. `AUTH_INVALID_TEMP_KEY` = 凭证过期，重新取凭证后**查原 JobId**，不要重新提交。
5. **并发槽位上限 2**：同时在跑的任务最多 2 个，第 3 个提交返回
   `concurrent slot limit exceeded (2) for dimension hy-3d`。
   批量时串行提交，或最多 2 个并发——推多了照样被拒，而**反复重试提交
   会把日志刷爆**（见过一次 55 分钟刷出两千行 429，真正有用的信息全被埋了）。
   注意这条和"每日 5 次"是两个计数器：并发满了不代表当天次数用完，
   等前一个跑完就能提交，**不要因此判定额度耗尽而中止整批**。

## Step 3：压缩与内嵌

原始 GLB 通常 20~24MB（三张 4096² PNG 贴图），网页里没法用。

```bash
py scripts/prep_actor.py raw/xxx.glb out/xxx 1024
```

做四件事：贴图压到 1024² JPEG(q88) → 重排 bufferViews 并做 4 字节对齐 →
写精简 GLB → 转成 base64 的 `.js`（`window.ACTOR_XXX`）。
体积降到 **0.4~0.5MB**，面数不变。同时打印 bbox、面数、**最长轴**——
最长轴就是身高方向，别假设是 Y。

**为什么要 base64 内嵌**：`file://` 协议下 `fetch`/`XHR` 会被 CORS 拦死，
`GLTFLoader` 直接不可用。`<script>` 标签不受此限制，所以把二进制塞进 JS 字符串。
若你的项目本来就跑在 http server 上，可以直接 fetch，省掉这一步。

## Step 4：运行时加载

用 `assets/glb-lite.js`：极简 GLB 解析器，只依赖 three 的 `BufferGeometry`。
支持 POSITION/NORMAL/TEXCOORD_0、uint16/uint32 索引、baseColor/normal 贴图、
node TRS。**不支持骨骼与动画**（这也是为什么 Step 6 要造伪骨骼）。

两个致命细节：

- **glTF 的 UV 原点在左上（V 向下）**，与 three 的 `flipY` 相反。
  自己采样贴图时必须写 `ty = v * (H - 1)`；写成 `(1 - v) * (H - 1)` 会渲出一堆错位色块。
- 不同生成器的**上轴不一致**，有 Z-up 也有 Y-up。进游戏前先读 bbox 判断最长轴。

## Step 5：接进游戏

照 `assets/glbActor.template.js` 抄，核心四条：

1. **按目标身高缩放**：`k = 目标身高 / 模型高`，不要硬编码缩放值。
   **趴姿 / 横长的模型要反过来按宽度定标**——这类模型宽是高的 1.6 倍以上，
   按身高缩放会把宽度一起放大成一团趴地蒲团。给 `glbActor` 传 `w`（目标全宽），
   身高由宽度反推。
2. **脚底对齐**：`position.y = -bbox.min.y * k`，否则模型半截埋地或悬空
3. **碰撞盒按真实包围盒重算 + 固定宽容，两个方向都别照抄**。旧手写模型的判定
   通常比视觉宽（视觉 0.5 米宽的豆包，判定半径给到 0.66）—— 照新包围盒算
   会让玩家"擦过去都不算撞"；但**照抄旧值**更糟：AI 模型往往瘦一大圈，
   豆包 AI 版实际深 0.41 米，旧判定深 1.76 米，比模型宽出 1.35 米，
   玩家看着模型过去了、看不见的盒子还锁着 —— 空气墙。
   正确做法：`hx = 视觉半宽 × 缩放 + 0.05`。判定深超过视觉深 0.3 米就该警惕
4. **缓存原型**：`GLB_ACTOR_CACHE[jsVar]` 存解析结果，每次 `clone(true)`。
   重复解析 = 重复解码贴图，火焰图立刻炸

失败路径一定要留：`glbActor()` 在模型缺失/解析失败时返回 `null`，
调用方 `var a = glbActor(...); if (!a) return 旧的函数();`。
这样模型没生成出来游戏也能跑，可以边等生成边开发。

## Step 6：补齐 AI 模型的三个短板

### 6.1 无骨骼 → 伪骨骼

按「离地高度 × 侧向距离」算顶点权重，绕髋点旋转 `position` 和 `normal` 两个
BufferAttribute。**轴心必须用同一套坐标系**——这是最容易错的地方：
若 `h = -raw_z`（脚底 −0.95、头顶 +0.95），髋点在此系里是 **−0.33**；
直接拿世界坐标的 `0.62` 用，轴心会跑到头顶，"腿"的判定变成"除头以外的一切"，
整个身体绕脑袋甩成钟摆。

权重只按高度算不够：肚子下缘会跟着腿扭起褶。必须乘一个横向权重，中线不动。

### 6.2 五官穿模 → 不要覆盖，先查贴图

**先确认贴图里五官到底在哪，再决定要不要盖。** 典型误判：按左右对称盖一对眼球，
结果 AI 贴图是 3/4 侧脸，双眼实际在 x=−0.211 / +0.038 完全不对称，
盖上后一颗浮在头顶、一颗压在脸颊。

正确做法：眼睛只补高光点，不覆盖原贴图；需要眨眼就压扁原有眼部区域。

嘴更难：笑缝在 3D 里是弯的（z 从 +0.26 到 +0.18，差 8cm），任何解析曲面贴上去
必然有一端顶出脸颊。解法是从**模型表面采样**生成"贴脸凹片"：正交光栅化 + z-buffer
反查真实曲面坐标，沿法线抬 4mm。开合时缩放顶点前，必须先把顶点变换到局部坐标系，
否则缩放绕原点进行，嘴会瞬移到肚子上。

### 6.3 姿势不对 → 判断值不值得修

模型会保留参考图的姿势。举着的手、外八的腿，在静态展示里没问题，跑起来就像挥手。
小角度（<30°）可以靠伪骨骼补，大角度（70~100°）会让腋下压出褶——因为手臂是连在
躯干上的整体网格。这种要么接受，要么换一张双臂自然下垂的参考图重跑。

### 6.4 模型高度 = 玩法定位，先想清楚再定标

模型一旦按身高缩放，它就成了一个「多高」的障碍物，而高度直接决定玩家能不能跳过去。
**别用最高点比大小来判断**——这是最容易踩的错：

```
最高点 1.80 米 > 障碍顶 1.47 米   ← 看起来能跳，实战 100% 撞
```

真正决定成败的是两个持续时间之比：

| 量 | 怎么算 |
|---|---|
| 脚底高于障碍顶的窗口 | 解 `Vt − ½Gt² = hitH`，两根之差 |
| 障碍穿过判定区的时长 | `2 × (hz + 玩家半深) / 当前速度` |

窗口必须**明显大于**后者。**验收指标是窗口秒数，不是容错米数**：
`窗口秒数 = (窗口上沿 − 下沿) / 当前速度`，可跳障碍要 ≥ 0.25 秒
（低于这个人类反应不过来，「能跳」名存实亡）。
玩家「看到障碍就跳」的本能落点在 6~8 米外，窗口要罩住这个区间。

调法上有个反直觉的结论：**想让低障碍变好跳，别降 `hitH`（会造成视觉穿模），
降 `GRAVITY`**。高度 `V²/2G` 只取决于 `V²/G`，同时按比例调 `V` 就能保持最高点不变，
而抛物线变「平」，窗口自然变长。实战数据：`13.6/52 → 7.1/14`，
最高点几乎不变（1.78 → 1.74），豆包的窗口从 0.16 秒变成 **0.34 秒**。

另一个常被漏掉的杠杆是**判定盒深度 hz**：趴姿模型纵向很长，
深度决定玩家「要在它上方待多久」。刀盾 1.44 米长，hz 0.72 → 0.42，
窗口立刻翻倍 —— 撞击触发点缩到 0.88 米仍在模型轮廓内（鼻子在前 0.95 米），看不出差别。

反过来说，要让某类障碍「永远跳不过」，就把它的判定顶抬到**高于跳跃最高点**
并留 0.1 米余量（数值积分会抖）。硬撑 `hitH` 到视觉高度之上会让玩家撞到看不见的空气。

**但「谁能跳」这件事必须显式写出来，别让它由高度隐式决定。**
靠 `if (hit.y1 <= 1.80)` 反推，等于说「改一下 `hitH` 就等于悄悄改规则」——
哪天有人为了调视觉把某只从 1.58 抬到 1.86，它的玩法定位就变了，而代码里没有一处记录。
正确做法是一张名单 + 模型跟上名单：

```js
var OB_JUMPABLE = { bun: true, shield: true,            // 能跳的
                    niulai: false, cow: false, lulu: false, pigman: false };
```

- 说「只能躲」，就把模型**真做高**到跳不过去（本例 1.72 → 1.96，判定顶 1.88 > 上限 1.80）
- 让**大小本身就是线索**：能跳的都在 1.7 米以下，跳不过的全在 1.9 米以上
- 改完跑 `tools/jump_check.py` 核对（它会读 `OB_JUMPABLE`，逐条验物理是否与规则一致）

详见 `references/pitfalls.md` 第 14 条。

## 交付前自检

- [ ] 模型在目标尺寸下比例正确，没被拉成"蒲团"或"竹竿"
- [ ] 脚底贴地，不埋不悬
- [ ] 碰撞盒手测过：能撞到，也不至于隔着半米就判撞
- [ ] 关掉新模型（开关置 false）游戏仍能跑，旧模型兜底有效
- [ ] `file://` 直接双击打开能显示（不是只在 dev server 下正常）
- [ ] 移动端小屏与桌面大屏各看一次
