# 踩坑清单

按「症状 → 真因 → 改法」排。绝大多数不是参数没调好，而是**坐标系或假设错了**。
遇到怪现象先怀疑坐标系，别先调数值。

## 速查表

| 症状 | 真因 | 改法 |
|---|---|---|
| 跑起来整只绕脑袋甩，像钟摆 | 铰点用了世界坐标，顶点用模型坐标 | 轴心换算到同一套坐标，见 1 |
| 嘴/眼一部分陷进脸里，一部分浮在外面 | 脸是曲面，贴平的东西必然一头顶出 | 从模型表面采样生成凹片，见 2 |
| 开合嘴时嘴瞬移到肚子 | 缩放绕物体原点进行，顶点是绝对坐标 | 顶点先变换到局部系，见 3 |
| 一对眼睛一颗浮头顶一颗压脸颊 | 贴图里双眼本来就不对称 | 别覆盖，只补高光，见 4 |
| 模型缩成一坨 / 躺在地上 | 上轴不是 Y | 读 bbox 最长轴，见 5 |
| 贴图渲成错位色块 | glTF 的 V 轴向下，自己采样时方向写反 | `ty = v*(H-1)`，见 6 |
| 网页打开一片空白，console 报 CORS | `file://` 下 fetch 被拦 | base64 内嵌 + `<script>`，见 7 |

| 玩家从角色身边擦过去不算撞 / 撞上空气墙 | 碰撞盒照抄旧模型，而 AI 模型瘦一大圈 | 按真实包围盒 + 5 厘米宽容重算，见 9 |
| 第 6 个角色提交不上 | 每日 5 次**次数**额度 | 排优先级，见 10 |

## 1. 跑姿像钟摆：两套坐标系混用

**症状**：腿一摆，整只角色（包括头）绕脑袋转，像挂钟的摆锤。

**真因**：伪骨骼需要一个髋部轴心。顶点高度算的是 `h = -raw_z`
（模型空间，脚底 −0.95、头顶 +0.95，范围 1.9），但轴心写成了世界空间的
`HIP_Y = 0.62`。这个 0.62 在 `h` 系里根本不存在——它大于 0.95，
于是轴心落在头顶之外，"腿"的判定条件 `h < HIP_H` 变成"除头以外的一切"。

**改法**：先统一坐标系，再算轴心。

```js
// 世界坐标的髋高 0.62，减去脚底的 0.95，得到模型空间的 -0.33
var HIP_H  = -0.33;   // 铰点高度（模型空间）
var LEG_CUT = 0.22;   // 超过这个高度完全不受腿影响
var LEG_GAIN = 0.80;
```

**通用教训**：任何"轴心 + 顶点"的组合，先打印两者的坐标范围确认在同一个系里。
一次 `console.log(min, max)` 能省两小时。

## 2. 五官穿模：曲面贴平面必然失败

**症状**：贴上去的嘴，左端陷进脸颊，右端悬空。

**真因**：笑缝在 3D 里是**弯的**——从嘴角到中间，z 从 +0.26 变到 +0.18，
前后差 8cm。任何解析曲面（球面、椭球、抛物面）贴上去，只要形状和真实
曲面不完全一致，就必然有一端顶出来。这不是参数调不调得好的问题。

**改法**：不要再"贴一个东西上去"，改成"从模型表面抠一块下来"。

1. 用正交投影把模型光栅化一遍，记录每个像素对应的**真实曲面坐标**（z-buffer 反查）
2. 在屏幕上圈出要贴的区域，按像素取回对应的 3D 坐标
3. 沿该点法线往外抬 4mm，生成一张贴合曲面的薄片网格
4. 把这张薄片当独立物体做开合动画

实测：一张 131 顶点的凹片就够覆盖整个笑缝，比任何解析曲面都准。

## 3. 缩放后零件瞬移：顶点是绝对坐标

**症状**：`scale.y` 从 1 改到 0.6 想让嘴闭上，结果嘴跳到肚子上。

**真因**：`Object3D.scale` 是绕**物体自身原点**缩放的。如果你的网格顶点存的是
模型绝对坐标（比如嘴在 `y=0.35`），而这个物体的原点在 `(0,0,0)`，
那 `scale.y = 0.6` 会把嘴从 0.35 拽到 0.21——它没有在原地压扁，而是朝原点缩过去了。

**改法**：把顶点写成相对物体原点的坐标。

```js
// 生成凹片时：先把顶点整体平移，使区域中心落在原点
for (var i = 0; i < n; i++) {
  pos[i*3+0] -= cx;
  pos[i*3+1] -= cy;
  pos[i*3+2] -= cz;
}
// 然后把物体放到 (cx, cy, cz)，之后 scale 才是"原地压扁"
mouthG.position.set(cx, cy, cz);
```

## 4. 眼睛一颗浮一颗陷：贴图本来就不对称

**症状**：按左右对称盖了一对眼球，结果一颗飘在头顶上方，一颗压在脸颊上。

**真因**：AI 生成的是 3/4 侧脸。贴图里双眼实际位置是 `x = −0.211` 和 `x = +0.038`，
根本不是对称的 ±0.132。你按对称盖，两个都盖错了地方。

**改法**：**先测量，再决定要不要盖**。

- 用正交光栅化 + z-buffer 把屏幕坐标和模型局部坐标对应起来，叠网格读数字
- 多数情况下正确答案是**不覆盖**：只补一个白色高光点，保留 AI 的原始眼眶
- 需要眨眼就把原有眼部区域压扁（`scale.y = 0.17`），别另建眼球

**方法论**：不要假设"AI 做崩了"。先量。这一条推翻过一次错误结论。

## 5. 上轴不是 Y

**症状**：模型躺在地上，或者被压成一个扁片。

**真因**：glTF 本身不规定上轴。不同生成器会给 Z-up 或 Y-up。生成器给的是
**Z-up**，代码按 Y-up 缩放，于是"高度"取了模型的厚度。

**改法**：看 `prep_actor.py` 打印的 `AXIS 最长轴 = ?`。角色类模型最长轴就是身高方向。
如果最长轴是 Z，缩放和"脚底对齐"都要换成 z 轴口径，或者进 three 后先
`rotation.x = -Math.PI/2` 转成 Y-up，再统一按 y 处理。

## 6. 贴图采样方向反了

**真因**：glTF 的 UV 原点在**左上**（V 向下），three 的 `Texture` 默认
`flipY = true`（会翻过来）。自己写采样代码时如果按 three 的习惯写，
就会取到上下镜像的像素，渲成一堆错位色块。

**改法**：自行采样贴图时写 `ty = v * (H - 1)`。
写成 `ty = (1 - v) * (H - 1)` 就错了。

## 7. `file://` 下加载失败

**真因**：双击 HTML 打开时，`fetch` / `XMLHttpRequest` 读本地文件被 CORS 拦。
`GLTFLoader` 内部就是 fetch，所以完全不可用。

**改法**：base64 内嵌进 `.js`，用 `<script>` 引入——script 标签不受 CORS 限制。

```html
<script src="lib/glb-lite.js"></script>
<script src="models/nailong_glb.js"></script>   <!-- window.ACTOR_NAILONG = "..." -->
```

运行时 `GLBLite.loadB64(window.ACTOR_NAILONG)`，全程不碰网络请求。
若项目本来就跑在 http server 上，可以省掉这步直接 fetch。

## 8. 体积过大

**真因**：不是面数多（低模只有 1 万面），是**三张 4096² PNG**，共 22MB。

**改法**：压贴图，不减面。1024² JPEG q88 后总计 0.4MB，降 50 倍。
减面会把五官减崩，得不偿失。

## 9. 碰撞判定失准

**症状**：玩家明明撞上了却穿过去；或者离着半米就判撞；
或者「看着已经跑到身后了还是撞死了」—— 空气墙。

**真因**：两个方向都会出错。旧的手写模型碰撞盒是**手调的**，通常比视觉宽得多
（视觉 0.5 米宽，判定半径给到 0.66，为了让手感宽容）：

- 照新的视觉包围盒算 → 判定突然变严格，玩家体感「擦过去都不算撞」
- **照抄旧值** → AI 模型往往比手写的瘦一大圈。豆包就是现成的例子：
  AI 模型实际深 0.41 米，旧判定深给的是 1.76 米，比模型宽出 1.35 米，
  玩家看着模型已经过去了，那个看不见的盒子还锁着 —— 这条比上一条恶劣得多，
  因为玩家完全看不见自己错在哪。

**改法**：**两个都别照抄，按真实包围盒重算 + 固定宽容**：
`hx = 视觉半宽 × 缩放 + 0.05`（宽容 5~6 厘米，肉眼不可见）。
`glbActor` 支持 `opt.hx / opt.hz` 覆盖，但覆盖值也应该是重算出来的，
不是从旧模型搬来的。

**验证**：把模型的 GLB 包围盒和 `glbActor` 的入参放一起对一遍，
判定深超过视觉深 0.3 米以上就该警惕。

## 10. 每日 5 次额度 + 并发槽位 2

两个独立的计数器，别混：

| | 每日提交次数 | 并发槽位 |
|---|---|---|
| 上限 | 5 次 / 自然日 | 2 个同时在跑 |
| 报错 | `daily submit limit exceeded (5/5)` | `concurrent slot limit exceeded (2)` |
| 何时恢复 | 0 点重置 | 等前一个任务跑完 |
| 撞了怎么办 | 停止，改天 | 等，**不要判定额度耗尽而中止整批** |

- 维度 `hy-3d`，**每天 5 次提交**，与账户积分是两套账，积分再多也提不上去
- 超限：`HTTP 429` + `daily submit limit exceeded (5/5) for dimension hy-3d`
- 按**自然日 0 点**重置，不是提交后 24 小时
- 提交顺序：**先跑图最差的**。图需要补全身的最费事，排在前面；
  一张高质量白底正面图 5 分钟就成，排最后不亏
- 提交成功立刻把 `JobId` 写盘。生成 5~15 分钟，脚本超时很常见，
  没写盘就得重提 = 白烧一次额度
- **并发槽位满了不要反复重试提交**。见过一次脚本对同一个角色连推几十次，
  55 分钟刷出两千行 429，真正有用的状态行全被埋掉。正确做法是等，
  或者只对"还没提交成功"的角色尝试，成功的进轮询队列

## 11. 姿势搬进了模型

**症状**：模型看着挺好，一跑起来像在挥手/外八。

**真因**：生成会保留参考图的姿势。手举着就一直是举着的。

**改法**：
- 小角度（<30°）用伪骨骼补，调手臂权重绕肩旋转
- 大角度（70~100°）不要硬拧——手臂和躯干是**一整块网格**，大角度会在腋下
  压出褶皱。正确解是换一张双臂垂放的参考图重跑（见 reference-image.md）

## 12. 其它零碎

- **`model 3.1` 不支持 `LowPoly`**。要用低模必须指定 `3.0`
- **收集物别做 360° 旋转**。抽象几何体旋转没问题，有脸的模型一转就露出后脑勺，
  像商品展示台。改成小幅摆头（±0.55 rad）+ 上下浮动
- **调试摆位一摆出来就撞死**：把障碍物摆到玩家车道上导致的。调试时摆在
  两侧车道（0 / 2 道）并冻结世界推进
- **截图截不到静止角色**：跑几帧就过去了。摆位后冻结世界再截
- **生成图右下角有平台水印**：不能裁剪（会切到鞋底），采样背景色涂平

## 13. 看着能跳过去，实战百分百撞

**症状**：障碍物的判定顶明显低于跳跃最高点（1.47 vs 1.78），玩家起跳也能跨过去，
但十次十次撞死。玩家会认为「判定写错了」。

**真因**：不是判定，是**时间**。两个量刚好卡在一起：

```
脚底高于 1.47 的窗口 : 0.218 秒     ← 抛物线在顶部有多平
障碍穿过判定区时长   : 0.214 秒     ← 2×(hz 0.88 + 玩家半深 0.46) / 12.5 m/s
```

窗口只比需求多 0.004 秒，换算成距离是 **3 厘米**。等于要求按键精确到一帧，
人类不可能做到 —— 手感上就是「跳不过」。

**改法**：别降 `hitH`（会让玩家脚底穿过障碍头顶，视觉穿模），**降 `GRAVITY`**：

| | 改前 | 改后 |
|---|---|---|
| `JUMP_V / GRAVITY` | 13.6 / 52 | 10.4 / 30 |
| 最高点 | 1.778 | 1.803（几乎不变） |
| 滞空 | 0.52 s | 0.69 s |
| 1.47 处窗口 | 0.22 s | 0.31 s |
| 起步速度下容错 | 0.13 米 | 1.15 米 |

关键点：最高点只由 `V²/(2G)` 决定，`V` 和 `G` 按同比例降就能保持高度，
而抛物线整体变「平」，窗口自然变长。**高度不变，手感质变。**

配套的两条约束：

- 要让某类障碍「永远跳不过」，把它的判定顶抬到**高于跳跃最高点并留 0.1 米余量**
  （数值积分会抖）。这里 1.80 的上限就是卡着噜噜 1.90 / 猪猪侠 1.98 定的
- 定完参数用 `tools/jump_check.py` 验算容错米数，别靠试玩感觉。
  容错 < 0.5 米就是不可用

**顺带**：模型放大缩小会直接改变它的玩法定位。同一只角色从 1.37 拉到 1.72，
「可跳」就变成「要准」，再高就变成「只能换道」。定标前先想清楚要它承担哪种角色。

**另一个隐藏因素：判定盒的深度（hz）**。趴姿的刀盾纵向 1.44 米，判定深 0.72
意味着玩家要在它上方待 2.4 米的路程。把判定深收到 0.42（模型鼻子在前 0.95 米，
0.88 米处触发碰撞时玩家正好贴着它的脸，看不出差别），窗口立刻从 0.16 秒
涨到 0.32 秒。**深度决定「要跳多久」，高度决定「跳多高」—— 两个都要查。**

## 13.5 「能跳」要按秒数验收，并用真实代码回归

上面 13 条的「容错 1.15 米」后来被证明是**误导性指标**：1.15 米除以 12.5 m/s
只有 0.09 秒的反应余量，照样百分百撞死。正确的验收指标是**窗口秒数**：

```
窗口秒数 = (窗口上沿 - 窗口下沿) / 当前速度
```

- **< 0.25 秒**：人类基本反应不过来，「能跳」名存实亡
- **0.3 秒以上**：看得到、来得及，正常玩家能过
- 玩家「看到障碍就跳」的本能落点在 6~8 米外 —— 窗口要罩住这个区间

**怎么算才可信**：公式推算和真实代码之间可能差一个 `>=` 号。
最可靠的是在游戏里加一个**确定性模拟**入口（`#simtest`）：固定 1/60 步长、
逐帧调用真实的 `updateWorld / updatePlayer / checkCollisions`，
对每个角色扫出「从几米外起跳能过去」的完整区间，结果写进 DOM，
headless 下 `--dump-dom` 直接读 —— 不渲染、不抓帧、完全可复现：

```bash
chrome --headless=old --dump-dom --virtual-time-budget=40000 \
       "index.html#simtest" | grep RESULT
# RESULT 豆包 v=12.5 峰=1.742 可跳=4.10~8.40 容错=0.34s
```

再配一个 `#simtest&jv=8.9&jg=22&shz=0.72` 式的参数覆盖，调参扫描不用改源文件。
离线脚本（`jump_check.py`）和 simtest 的结果应该一致（差 0.1 米以内），
不一致时以 simtest 为准 —— 它跑的就是玩家真正会撞到的那个判断。

## 14. 「能不能跳」不该靠高度反推

**症状**：没人改跳跃参数，也没人改规则，但某只障碍的玩法定位忽然变了。
或者反过来 —— 想改一只角色的定位，发现改了半天模型，判定还是老样子。

**真因**：可跳性是用隐式条件判断的：

```js
if (ob.hit.y1 <= 1.80) { /* 当作可跳障碍，试跳 */ }
else                   { /* 当作必须换道，找空道 */ }
```

`1.80` 是跳跃最高点。这条规则能跑，但有三个问题：

1. **改 `hitH` 就等于偷偷改规则**。把某只障碍从 1.58 调到 1.86，它就从「可跳」
   变成「只能躲」，而代码里没有任何一处写着这件事。半年后没人说得清为什么这只不能跳。
2. **反过来也成立**。有人为了「让它显得高一点」把 `hitH` 抬到 1.79，
   它会一直留在可跳名单里，但容错只剩几厘米 —— 玩家觉得「明明跳过去了」。
3. **模型身高和规则脱钩**。判定顶 1.88、模型却只有 1.72 的话，玩家脚底明明高过
   它的头顶还是撞死，第一反应就是「这游戏有 bug」。

**改法**：把名单显式写出来，让高度只负责手感。

```js
// 哪些障碍「跳得过去」，只有这两个，其余一律换道
var OB_JUMPABLE = { bun: true, shield: true, niulai: false, cow: false,
                    lulu: false, pigman: false };

// 生成实体时带上，判定处只认这个字段
addEntity(obj, 'obstacle', Z, { hit: o.hit, name: o.name,
                                jumpable: OB_JUMPABLE[type] === true });
```

配套三条：

- **模型要跟上判定**。说它只能躲，就把模型真做高到跳不过去（这里 1.72 → 1.96，
  判定顶 1.88 > 跳跃上限 1.80）。别只抬判定数字。
- **让大小本身就是线索**：能跳的两个在 1.7 米以下，跳不过的全在 1.9 米以上，
  玩家看体型就能判断，不用背名单。
- **把规则做成可核对的东西**。`jump_check.py` 会从 `game.js` 里读 `OB_JUMPABLE`，
  再用真实物理参数逐条验「说能跳的真有正容错 / 说跳不过的真够不着」，对不上就 exit 1。

**顺带一个调试坑**：验证「脚底 vs 障碍头顶」时，障碍和玩家**不在同一深度的话，
屏幕像素高度不能直接比** —— 远处的会被透视压到更高，看起来像过得去。
`#show` 摆的障碍在 `z=-4.6`、玩家在 `z=0`，用那个截图判断高低是错的。
要用同一个深度（`#hop` 摆到 `z=-0.6`），并且**别靠抓腾空帧**：
headless 的虚拟时间和游戏时间不同步，抓到的是刚起跳那一瞬。
最稳的是给玩家一个「钉死高度」的调试参数，纯静态摆位。

## 15. 窗口够宽还是跳不过：把「矮」做进模型，把「时机」画到地上

**症状**：判定盒照实算了、窗口秒数也验收过了（0.32~0.34 s），玩家反馈还是
「跳不过去」。数值全对，手感全错。

**真因**：0.3 秒出头的窗口对「键盘按一下」是够的，但跑酷玩家的真实操作链是
「看到障碍 → 判断距离 → 决定起跳」，整条链吃掉的时间比窗口本身还长。而第三人称
追尾视角下，**玩家根本没有可靠的深度参照物**去判断「还差几米」——你量得出窗口，
玩家量不出。继续磨判定盒、磨抛物线，都是在给错误的问题做优化。

这一版的峰值也被锁死了：不可跳的牛来判定顶 1.88、模型 1.96，跳跃峰值压到 1.74
就再也抬不动 —— 「加高跳跃」这条路的终点早就到了。

**改法（三条，都是结构性而不是调参）**：

1. **可跳的东西就做成矮的**。豆包 GLB 出来 1.49 米就直接用 1.49，从来没人问过
   「它该多高」。按人设它就是矮个 —— 重定到 1.05 米后，判定顶 1.00，玩家从她头顶
   跨过去，视觉和判定同时成立。**别让「模型出来多大就用多大」替你做设计决定。**
2. **判定顶 ≠ 模型全高**。刀盾趴姿 1.63 米里有半米是竖起来的刀和盾，身体本体
   远没那么高。判定顶取「挡路的那部分」的高度（1.05），不是包围盒最大 y。
3. **把起跳窗口画出来**。窗口区间 [t1·v+half, (t2-span)·v+half] 游戏自己算得出来，
   就让障碍进入这段距离时在脚下亮一个脉冲绿环+向上箭头（`jumpCueRange` /
   `updateJumpCue`）。玩家看到亮就按，时机从「心算深度」变成「看灯」。
   注意 cue 的材质要新建，别用共享缓存的 `matB` —— 每帧改 opacity 会污染别处。

**配套手感**（没有这三条，宽窗口也会被「按了没反应」吃掉）：
- 土狼时间 0.10 s：离地瞬间仍可起跳；
- 跳跃缓冲 0.13 s：落地前按跳，落地帧自动兑现；
- 判定容差从「×0.95 百分比」改成固定 6 cm——百分比折扣对矮障碍几乎没收益。

**验收**：`#simtest` 的 `simBot()` 用固定步长连跑 3×30 秒完整局（真实
updateWorld/updatePlayer/checkCollisions + bot 自动跳/换道/蹲），死亡 0 才算过。
不要信 `#bot` 的 rAF 统计 —— headless 虚拟时间推不动 rAF，那个数字是假的。
bot 自己也要写对：跳跃预测必须用欧拉积分（解析抛物线峰值高 7 cm，边界帧会
「以为能过」）；横杆跨三道，近障碍表要按判定盒覆盖算，只看中心所在道会看不见它。
